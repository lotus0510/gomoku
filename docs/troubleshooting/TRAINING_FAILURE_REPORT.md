#### Bug 診斷過程

**調查結果**：
- ✅ MCTS Dirichlet 噪聲應用正確 (`core/mcts.py:168-185`)
- ✅ 溫度控制使用配置正確 (`train_pipeline_pytorch.py:126-132`)
- ✅ 探索參數正確傳遞給所有進程
- ✅ 配置正確分發到自我對弈 worker
- ❌ **學習率調度器加載舊狀態** (LR_DECAY_STEPS=100) 但使用新配置 (LR_DECAY_STEPS=200)
- ❌ 導致優化器學習率錯亂，無法正確更新權重

**Bug 機制**：
```
1. 前 20 次迭代：用舊配置 (LR_DECAY_STEPS=100)
2. 改用優化配置 (LR_DECAY_STEPS=200)
3. 從檢查點恢復時：
   - 模型權重：✅ 正確加載
   - 優化器狀態：✅ 正確加載
   - 調度器狀態：❌ 加載舊狀態 (100 步)，但新配置說 200 步
   - 配置參數：❌ 從未從檢查點恢復
4. 結果：
   - 調度器以為在第 X 步（基於舊配置）
   - 但應該在第 Y 步（基於新配置）
   - 學習率完全錯誤
   - 策略網路幾乎無學習，價值網路崩潰
```

#### Bug 修復方案

**修改文件**：`train_pipeline_pytorch.py`

**修復位置**：
- 第 437-477 行：明確指定檢查點恢復路徑
- 第 479-527 行：自動檢測檢查點恢復路徑

**修復邏輯**：
```python
# 1. 從檢查點讀取保存的配置
saved_config = checkpoint.get('config', None)

# 2. 比較關鍵參數是否變更
if saved_config.get('LR_DECAY_STEPS') != config.LR_DECAY_STEPS:
    config_changed = True

# 3. 如果配置變更
if config_changed:
    # 重新創建調度器（使用新配置）
    scheduler = torch.optim.lr_scheduler.StepLR(
        optimizer,
        step_size=config.LR_DECAY_STEPS,
        gamma=config.LR_DECAY_RATE
    )
    # 將調度器推進到當前迭代
    for _ in range(current_iteration):
        scheduler.step()
else:
    # 配置未變，正常加載調度器狀態
    scheduler.load_state_dict(checkpoint['scheduler_state_dict'])
```

**修復效果**：
- ✅ 配置變更時自動重新初始化調度器
- ✅ 調度器與當前迭代同步
- ✅ 學習率正確應用
- ✅ 兩個恢復路徑都已修復

## 二、根本原因分析

### 2.1 主要原因：探索參數過高

#### DIRICHLET_EPSILON = 0.35 (過高)

**問題機制**:
```
MCTS 根節點策略 = 0.65 × 神經網路預測 + 0.35 × 隨機噪聲

訓練目標中 35% 是隨機噪聲
↓
網路學習的是「接近均勻分布」
↓
策略損失無法下降
```

**影響鏈**:
1. 自我對弈生成的策略標籤有 35% 隨機性
2. 神經網路嘗試擬合這些隨機標籤
3. 最優策略變成「輸出接近均勻分布」
4. Top-1 機率極低 (0.008)，無明確策略
5. 遊戲無防守意識，平均 23 步結束

**數據支撐**:
- AlphaZero 原版使用 DIRICHLET_EPSILON = 0.25
- 圍棋/象棋成功案例通常 < 0.20
- 我們的 0.35 比標準高 40-75%

**為什麼選擇 0.35？**
- 原始配置註釋：「從 0.25 → 0.35，+40% 探索性」
- 意圖：增強探索，避免過早收斂
- 結果：適得其反，探索過度導致無法學習

---

### 2.2 次要原因一：學習率過早衰減

#### LR_DECAY_STEPS = 100 (過早)

**問題機制**:
```
迭代 0-100:   LR = 0.0001 (初始學習率)
迭代 100:     LR = 0.0001 × 0.8 = 0.00008
迭代 200:     LR = 0.00008 × 0.8 = 0.000064

當前迭代 226: LR ≈ 0.00006
配合梯度範數 0.38 → 權重更新 ≈ 0.00002
```

**影響鏈**:
1. 迭代 100 時策略損失仍 > 5.2 (未收斂)
2. 學習率已開始衰減，學習速度減慢
3. 配合梯度消失 (0.38)，更新幾乎停止
4. 價值網路無法從崩潰狀態恢復
5. 訓練陷入停滯

**數據支撐**:
- 迭代 100-226 間，策略損失僅從 5.32 降到 5.28 (0.75% 改善)
- 價值標準差從 0.15 降到 0.11 (持續惡化)
- 梯度範數從 0.45 降到 0.38 (持續消失)

**為什麼選擇 100？**
- 原始配置註釋：「從 400 → 100，更頻繁衰減」
- 意圖：加速訓練後期微調
- 結果：訓練前期尚未收斂就開始衰減，學習停滯

---

### 2.3 次要原因二：溫度控制過於探索

#### TEMP_THRESHOLD_MOVE = 30, TEMP_FINAL_MOVE = 60 (過長)

**問題機制**:
```
步數 1-30:    溫度 = 1.0 → 完全隨機採樣
步數 30-60:   溫度線性降低 → 部分隨機
步數 60+:     溫度 ≈ 0 → 確定性採樣

平均遊戲長度 23 步 → 幾乎全程使用隨機採樣
```

**影響鏈**:
1. 前 30 步使用溫度 1.0，動作選擇完全隨機
2. 訓練數據中策略標籤隨機性極高
3. 神經網路無法學習明確策略
4. 遊戲很短 (23 步) → 幾乎無確定性階段
5. 進一步稀釋學習信號

**數據支撐**:
- 平均遊戲長度 23 步 < TEMP_THRESHOLD 30 步
- 大部分遊戲全程使用高溫度
- 配合 DIRICHLET_EPSILON 0.35，探索過度疊加

**為什麼選擇 30/60？**
- 原始配置註釋：「從 25/50 → 30/60，延長探索期」
- 意圖：增加策略多樣性
- 結果：遊戲太短，全程探索，無確定性階段

---

### 2.4 次要原因三：樣本多樣性不足

#### REPLAY_BUFFER_SIZE = 400,000 (偏小)

**問題機制**:
```
每次迭代生成數據: ~18,400 個樣本 (100 局 × 平均 23 步 × 8 對稱)
緩衝區容量: 400,000 樣本
保存迭代數: 400,000 / 18,400 ≈ 21.7 次迭代

訓練時抽樣範圍: 僅最近 20 次迭代
```

**影響鏈**:
1. 緩衝區只能保存約 20 次迭代的數據
2. 樣本多樣性不足，策略模式單一
3. 容易過擬合最近數據
4. 訓練不穩定，損失震盪
5. 無法利用早期高質量數據

**數據支撐**:
- 當前 226 次迭代，緩衝區已滾動 10+ 次
- 迭代 1-120 的 MCTS BUG 數據已被清空
- 迭代 120-200 的數據也大部分被清空
- 僅保留最近 21 次迭代

**對比**:
- AlphaZero 原版保存 50+ 次迭代
- 成功的五子棋 AI 通常使用 1M+ 樣本 (50-100 次迭代)
- 我們的 400K 偏小

---

### 2.5 次要原因四：MCTS 探索常數偏高

#### C_PUCT = 2.0 (偏高)

**問題機制**:
```
PUCT 公式: Q(s,a) + C_PUCT × P(s,a) × sqrt(N(s)) / (1 + N(s,a))

C_PUCT 越高 → 越傾向探索未訪問節點
C_PUCT 越低 → 越傾向選擇高 Q 值節點
```

**影響鏈**:
1. C_PUCT = 2.0 導致過度探索未知節點
2. 配合 DIRICHLET_EPSILON = 0.35，探索疊加
3. MCTS 搜索結果隨機性增加
4. 訓練目標不明確
5. 策略網路無法收斂

**數據支撐**:
- AlphaZero 圍棋使用 C_PUCT = 1.0-1.5
- 五子棋棋盤較小，應使用較低 C_PUCT
- 我們的 2.0 比建議值高 33-100%

## 三、停止訓練的決策依據

### 3.1 訓練已失敗的證據

#### 證據 1：策略損失無改善空間
```
當前策略損失: 5.28
隨機策略損失: 5.42
差距: 0.14 (2.6%)

結論: 幾乎無法區分訓練模型與隨機策略
```

**推論**:
- 226 次迭代後仍無明顯改善
- 當前配置下，策略網路已達到「學習隨機分布」的局部最優
- 繼續訓練只會浪費資源

#### 證據 2：價值網路無恢復跡象
```
價值標準差歷史:
迭代 1-50:    0.6-0.7 (健康)
迭代 51-120:  0.5-0.6 (良好)
迭代 121-150: 0.3-0.5 (開始下降，MCTS BUG 修復後)
迭代 151-200: 0.15-0.2 (持續惡化)
迭代 201-226: 0.11-0.13 (崩潰)

趨勢: 持續惡化，無恢復跡象
```

**推論**:
- 學習率已衰減到 0.00006，無法產生有效更新
- 梯度消失 (0.38)，即使增大學習率也難恢復
- 價值網路已陷入「輸出常數」的局部最優

#### 證據 3：梯度消失無法逆轉
```
梯度範數歷史:
迭代 100-150: 0.5-0.8 (健康下限)
迭代 151-200: 0.4-0.5 (開始消失)
迭代 201-226: 0.35-0.4 (持續消失)

當前 LR: 0.00006
有效更新: 0.00006 × 0.38 ≈ 0.000023
```

**推論**:
- 權重更新量級 < 0.0001，幾乎無變化
- 網路已陷入平坦區域，難以逃脫
- 需要更高學習率 + 更明確的訓練信號

## 七、風險與應對方案

### 7.1 風險 1: GPU 記憶體不足

**症狀**: 訓練啟動時 CUDA out of memory 錯誤

**原因**: BATCH_SIZE = 1024 需要約 4-6 GB GPU 記憶體

**應對方案**:
```python
# 方案 A: 降低批次大小 (優先)
config = TrainingConfig.get_optimized_config()
config.BATCH_SIZE = 512  # 降回原值

# 方案 B: 啟用梯度累積 (保持大批次效果)
config.BATCH_SIZE = 512
config.GRADIENT_ACCUMULATION_STEPS = 2  # 等效 1024
```

**重要**: 即使降低 BATCH_SIZE，也必須保持 DIRICHLET_EPSILON = 0.15

---

### 7.2 風險 2: 訓練時間過長

**症狀**: 每次迭代超過 1 小時

**原因**: EPOCHS_PER_ITERATION = 10, BATCH_SIZE = 1024

**應對方案**:
```python
# 方案 A: 降低 epochs (次優)
config.EPOCHS_PER_ITERATION = 5  # 降回原值

# 方案 B: 使用批量 MCTS (已啟用)
config.USE_BATCHED_MCTS = True  # 確保開啟
config.MCTS_BATCH_SIZE = 16     # 增加批次大小 (原 8)

# 方案 C: 減少自我對弈局數
config.GAMES_PER_ITERATION = 80  # 降到 80 (原 100)
```

**權衡**: 訓練時間 vs 收斂速度，建議至少保持 EPOCHS = 5

---

```
迭代 30:
├─ 策略損失 < 5.0 → 繼續訓練 ✅
├─ 5.0 ≤ 策略損失 < 5.2 → 降低 EPSILON 到 0.10，再觀察 20 次
└─ 策略損失 ≥ 5.2 → 重新檢查配置，可能需重新初始化
```

---

### 7.4 風險 4: 價值網路持續崩潰

**症狀**: 迭代 50 後，價值標準差仍 < 0.3

**可能原因**:
1. 價值損失權重過低
2. 學習率不足
3. 遊戲結果過於集中 (總是一方勝)
4. 梯度消失

**應對方案**:
```python
# 方案 A: 增加價值損失權重 (優先)
config.VALUE_LOSS_WEIGHT = 1.5   # 從 1.0 → 1.5
# 或更激進
config.VALUE_LOSS_WEIGHT = 2.0

# 方案 B: 使用更大的批次
config.BATCH_SIZE = 2048         # 如果 GPU 記憶體允許
# 或使用梯度累積
config.GRADIENT_ACCUMULATION_STEPS = 2

# 方案 C: 調整價值折扣
config.VALUE_GAMMA = 0.99        # 從 0.995 → 0.99 (稍偏效率)

# 方案 D: 增加溫度探索 (逆向操作)
# 如果遊戲結果過於集中，可能需要增加探索
config.TEMP_THRESHOLD_MOVE = 25  # 從 20 → 25
```

## 八、總結與建議

### 8.1 訓練失敗總結

**核心問題**: 探索參數過高 (DIRICHLET_EPSILON = 0.35) 導致訓練目標過於隨機

**連鎖反應**:
```
高探索噪聲 (35%)
  ↓
訓練目標隨機 (策略損失 5.28 ≈ 隨機 5.42)
  ↓
網路學習「均勻分布」
  ↓
價值網路失去判別能力 (標準差 0.11)
  ↓
梯度消失 (0.38) + 學習率過早衰減
  ↓
訓練完全停滯
```

**數據證據**:
- 226 次迭代後，策略損失僅比隨機好 2.6%
- 價值標準差從 0.68 崩潰到 0.11 (偏離 84%)
- 梯度範數低於健康下限 24%
- 遊戲無防守意識，平均 23 步結束

**結論**: 當前訓練已失敗，無挽救價值

---

### 8.2 優化方案總結

**核心策略**: 減少探索，增強學習

**關鍵修改**:
```
1. DIRICHLET_EPSILON: 0.35 → 0.15 (-57%)  🔴 最關鍵
   → 訓練目標從「接近隨機」變為「明確策略」

2. LR_DECAY_STEPS: 100 → 200 (+100%)      🔴 關鍵
   → 網路有足夠時間學習新的低噪聲訓練目標

3. REPLAY_BUFFER: 400K → 800K (+100%)     🔴 關鍵
   → 更好的樣本多樣性，減少過擬合

4. C_PUCT: 2.0 → 1.5 (-25%)               🔴 關鍵
   → 配合低探索噪聲，整體探索度下降

5. TEMP_THRESHOLD: 30 → 20 (-33%)         🔴 關鍵
   → 更快進入確定性階段，訓練信號更清晰
```

**次要優化**:
- EPOCHS_PER_ITERATION: 5 → 10 (加快收斂)
- BATCH_SIZE: 512 → 1024 (更穩定訓練)
- GRADIENT_CLIP_NORM: 1.0 → 5.0 (幫助恢復)
